- 原配置再次运行保留来源修订和条件；复制修改列出差异。模式改变、源码或知识不可取得时阻塞，不静默升级。创建响应丢失按原 request_id/plan_id 查证，不重复建 run。

## 原失败及边界

1. 早期 UI 的就绪等待假设和来源弹窗未立即加载问题保留在 initial/second UI 归档；来源弹窗修复后在固定最终代码复验。原先 7 项 UI 在中间版本也另有完整通过记录。
2. 首批临时库导出脚本误用 `ac_bookings`，实际表为 `sb_bookings`；通用测试清理在导出失败后删除了首批临时 SQL，因此**首批 SQL 没有完整保留**。这是助手遗漏，仅影响本轮首个隔离库；存活工具回执、日志、页面记录已归档。随后独立库导出已验证；新 OwnedDatabase 在导出校验成功且正常退出前不删库，异常保留 SQL、用户与相关 Redis。该保护有真实 SQL 控制检查。
3. 最终追加的等待输入控制夹具漏写 DSL 1.1，平台返回 409；原修订不改，另存修订 2。第一次补验的直接 HTTP 重放又遗漏 Origin，被会话保护正确以 403 拒绝；补齐测试请求头后重验通过。两份失败日志和控制修订记录保留，生产代码未因此放宽校验。
4. C 盘跌破 2GB 时停止一轮完整测试，隔离环境自动停机并保留数据库。一次重启测试遗漏 AC_INTEGRATION，191 过/240 跳过，不计为全量；随后正确启用真实 MySQL 的最终 431 项全部通过。原中断与不完整启动日志另存，不拼接成通过。
5. 第三次隔离环境因低空间停止后复用其保留数据库恢复，来源核对一致；没有抹掉失败重建成“始终成功”。恢复脚本正常结束时仍须先验证导出再清自有库。关闭 Codex 本体没有实际执行；已验证的是启动 CLI 退出后的独立后台监督，不能冒充前者实验。
