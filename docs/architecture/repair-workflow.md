# T17K 缺陷—修复—复测证据链

复用T15缺陷、人工复核artifact与比较器，复用T17H复制运行/预检流程；无新表、无自动修复或后台重跑。页面的条件核对是只读预览，最终状态仍由人工确认后通过原复核接口保存。

## 操作路径

运行详情 → 缺陷与报告 → 显式归并候选 → 查看候选与修复。缺陷列表也可进入；`/reports?tab=defects&defect=<key>`按当前身份读取并打开指定缺陷。

缺陷面板按原执行、修复版本、复测结论排列，提供原失败证据、复测草稿、条件逐项核对与历史验证跳转。关联修复版本不等于已修复；满足核对条件也不自动保存。

准备草稿跳到`/workbench?source=<run>&action=copy&repair_version=<version>`。只读取配置；复用原用例、故障、次数、种子及限制，当前可执行且同对象的修复版本才允许预选。不可执行不偷偷替换其他版本；正式创建仍须逐步核对、预检与确认，模型开关和预算不变。原运行若含保留/校准集，仍拒绝复制到开发流程。

## 只读核对与写入共用判据

`GET /api/v1/defects/{key}/verification?execution_id=<uuid>&fixed_version_id=<id>`：要求operator，缺陷及执行均属当前账号。返回缺陷修订hash、原/复测证据位置、逐项check、条件比较、版本变化与是否满足保存条件。等待中的运行只给未完成结果；取证错误不返回成功。

`POST /api/v1/defects/{key}/reviews`的verified决定重新运行相同判据：

- 缺陷已确认并先关联修复版本，且为客观规则候选；AI信号不能靠本流程自动升级为已验证。
- 新执行使用已关联的另一版本，运行completed、执行passed；取消、错误、等待和仍失败不能确认修复。
- 原失败规则仍为相应最新规则失败；原/新证据完整，保存评价的input_hash与当前完整证据一致。旧passed行不能掩盖已变化的SQL、输出或事件。
- 用例与独立预期、模型/SDK、知识、故障、重复次数、种子、限制、预算、额外人工输入、评价器及实际调用来源逐项一致；缺少记录即阻塞。参考时钟/fixture绑定在用例内容hash中。
- 同一缺陷指纹对应规则通过，最新规则组没有其他失败或不足。

源码/Prompt/策略等被测版本变化作为修复变量另展示；控制条件一致不证明单因素因果、统计显著或整体改善，不把当前开发复测当正式T16实验。

保存仍要求原缺陷expected_hash、人工作用声明、依据及原持久request_id；重复请求返回原回执。核对结果随复核artifact另存，不改写原断言、事件、SQL、真人标签或既有报告。角色/对象/选择变化清空旧预览，迟到核对结果不串入新上下文。

## 来源与验证边界

真实供应商、明确离线网关、浏览器传输控制、历史回放分开标示。受控版本元数据及离线策略仅检验本平台流程，不能作为真实Agent修复效果。本项不需要新模型调用；真实修复结论仅在实际代码修复与真实复测均存在时成立。历史T16无改善、T17B受限辅助与原分母保留。
