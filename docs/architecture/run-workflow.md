# T17H 日常执行服务与运行创建

## 本机执行服务

`scripts/workers.ps1 -Action start|stop|status|logs` 是显式本机运维入口，默认只管理当前项目 `main` 配置。它复用现有 D 盘 Docker Linux 引擎和已缓存的依赖镜像，不安装依赖、不新建 WSL。现有 `start-dev.ps1` 仍只启动前端/API。

Worker 与 Dispatcher 缺一不可。管理器核对实际数据库绑定、执行配置和队列，检查缓存镜像的依赖锁及关键 SDK 版本后，把当前源码/知识文件复制成只读快照挂载；镜像标签不作为当前源码的证明。每个实例保存独立标签、容器 ID、控制意图与心跳，操作只针对归属核验通过的容器。

后台监督进程与启动命令分离。异常退出按 2/4/8 秒退避，单次显式启动累计最多重试三次；持续失败保留状态，不无限重启。人工停止写入停止意图并结束容器，旧监督实例不能重新启动。Docker 不可达或归属变化时返回失败并保留容器身份，不谎报已停止，也不操作其他实例。主机重启后先恢复既有 Docker 引擎，再显式启动执行服务；关闭主机不能继续执行。

本地配置、密钥环境文件、日志与快照只在 D 盘 `.local/workers`，不进 Git、不经 HTTP 返回。普通页面不执行 PowerShell，不修改开关或初始化预算。`logs` 提供本地查看日志的准确命令；公开 API 只返回去凭据的就绪观察。

## 实际观察与有效期

- Worker 回执继承 T17C 的源码/Prompt/锁、数据库、执行配置和消费队列核验，并给出观察到的网关模式、活动任务和工作池容量；数据库有效租约另行核对，未知容量不当作空闲。
- Dispatcher 用独立实例键发布 12 秒 TTL 的观察，记录最近成功扫描。就绪需环境身份匹配、扫描成功、时间非未来且距今小于 15 秒、TTL 大于 0。存活心跳不能代替成功扫描；停止后可能保留短暂的尚未过期观察。
- 本机管理记录用于解释启动中、重启中、主动停止、失败或监督过期；它不代替消费者回执。远端或未托管部署显示未观察，不能从本机没有文件推断远端进程一定离线。
- 页面总就绪观察仍按 60 秒过期，失败或过期撤回“可用”。在线、容量、排队、实际执行来源、模型配置和授权各自显示。

## 预检与提交

原 `POST /runs` 的排队 API 兼容保留。新页面采用：

1. `POST /workbench/run-plans`：传 `RunPlan`，含原 `CreateRun` 配置、`new/rerun/copy` 意图、可选自有来源运行及 `ready/queue_only` 创建方式。核对权限、开发修订、哈希、基础知识兼容、目标版本及预算上限；只读查询环境，暂存短期 Redis 预检，不创建 SQL 运行、不调用模型。
2. 预检有效 60 秒，Redis 记录保留 90 秒，绑定身份、源码/数据库/执行环境、配置、输入修订及网关模式。阻塞不发可提交的 plan_id。`ready` 要求相应全部条件；`queue_only` 需用户显式选择，保留基础存储/版本检查，明确尚未执行。
3. `POST /workbench/run-plans/commit`：只接受原 `request_id/plan_id`。再次核对环境、原配置及就绪；客户端不能在提交时替换参数。创建仍调用原事务/幂等服务，写入不可变来源与差异。
4. 回执丢失按原请求与 plan_id 查证。已有自有匹配运行即返回原回执，即使预检缓存已过期；其他身份或其他计划不复用。前端在结果未知时冻结配置，不生成新请求重试。

新流程记录明确排队期限：从预检生成时起使用所选时限，提交时仍须未过期；首次领取前过期收尾，不调用模型或工具。领取后继续原执行墙钟限制。旧记录不补写新期限，租约/确认/未知提交原键查证规则继续适用。启动执行服务不初始化或清零账本，也不把原实验静默升级到新源码。

Dispatcher 在投递与过期收尾前核对每个运行的冻结源码、知识和执行配置；Worker 在领取前再次核对。旧配置不兼容时不投递、不领取，也不通过超时扫描改写该记录。核对使用该运行实际冻结的知识 ID，不把所有知识配置误当成基础知识。兼容性通过仍不替代租约、预算或幂等检查。

隔离环境的指引附带其已验证 profile；非 main 的再次启动只复用该 profile 保存在项目 `.local` 内、与原绑定一致的配置。默认 main 不继承隔离配置。不同 profile 的容器与配置不能串用。

## 再次运行与复制

`GET /workbench/runs/{run_id}/reproduction` 只读取自有开发运行；校准/保留集不进入开发复制流程。原配置再次运行保留可取得的用例修订、版本、种子、时钟、故障、重复和限制；条件或实际网关来源不同则阻塞。复制并修改明确列出差异，另建新运行并关联原 manifest_hash；原运行不改。人工追加输入不自动回放，需要在新运行中重新确认，不保证模型逐字一致。

历史回看只读原记录，不创建执行、不调用工具或模型。实际来源取持久执行的 `gateway_mode`；未观察到执行就显示未知/尚未执行，不凭“计划使用真实模型”宣称已经调用。明确离线模式只允许无密钥、四开关关闭的本项隔离验证库，通过可信依赖注入和专用控制 Worker 启用，日常页面不提供伪造离线入口。

## 验证导出

本项临时库由 `workflow_checks.storage.OwnedDatabase` 管理。导出使用明确模型对应的真实表名、RR 快照、ZIP CRC、逐表行数和 SHA256 校验；未核验的导出、失败导出不得触发删库，窄权限用户和相关 Redis 数据也保留。原 T17H 首批曾因预约表名错误而在通用测试清理中失去完整 SQL，错误与现存文件单列，不混入最终验证。最终验收以修复后的独立库与核验包为准。
