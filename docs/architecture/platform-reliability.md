# 平台可靠性与运行边界（T17）

业务写入仍使用 MySQL run→execution、预约时段锁和唯一约束，检查点与队列由 Redis 保存，Linux Celery 负责实际执行。租约失效只阻止后续写入，不能释放一个被操作系统暂停的进程已经持有的 SQL 事务锁。正常终止会断开连接；暂停时可能需要恢复或终止该自有进程才能释放锁。调度器会记录扫描错误并再次扫描，不自动重放可能已经提交的工具。

本轮先保留两个独立 run 追加事件时的真实1213复现，再把应用写连接改为 READ COMMITTED；MySQL全局默认隔离级别不改。缺失事件UUID的锁定查询不再产生原有的共享间隙锁冲突，同run的序列分配仍由run行锁串行保护。证据与运行详情的复合读取显式使用只读REPEATABLE READ快照，避免页面高水位与实际事件来自不同提交时点。

容量占满而未认领的消息会清除本次派发冷却标记，空位释放后可以立即重扫。它不会增加attempt或重新运行业务工具。重复消息仍须经过MySQL租约认领，重复输入仍用原请求ID/草稿/幂等键。

T17独立授权为1美元/最多60请求/每run最多0.10美元，生成器与裁判0。调用前Lua原子检查授权、运行、执行调用数与token预算；SQL票据镜像失败、缺usage或进程中断均保留预留。丢失授权账本拒绝调用，初始化标记禁止以重建代替恢复。金额与已结算用量是公开峰值费率估算，不能当作服务商账单。

验收工具在`backend/reliability/`，不进入生产wheel：`verify`使用明确离线模型和真实SQL/Redis/Linux任务；`real`使用真实ModelGateway与生产runner，只有预算Redis连接指向持久共享授权账本，并在真实provider片段后加入可观察暂停。任务/检查点始终使用独立Redis实例。真实与离线的范围、初始失败及最终验证分别保存，不能混为同一成功率。

运行命令与团队检查步骤见`docs/acceptance/T17.md`。固定15条每级的离线时延是同机小样本，不能当作DeepSeek吞吐量或生产容量；同机并行回归会影响时延。9条真实简短对话只证明连通与1/3/5调度，不能证明预约语义质量。已冻结T16的失败、人数来源和裁判协议缺口保持原结论。
