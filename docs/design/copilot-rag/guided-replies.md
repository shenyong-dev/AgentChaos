# 场景识别与引导式回复

2026-11-16 · 设计稿v0.2增补。用户要求回复细心、能识别问题对应场景并引导解决。本稿定义行为，尚未实现分类器、向量库或模型调用。与[语义向量RAG主设计](README.md)一起实施；不使用BM25。

## 1. 问题先对应到任务场景

助手综合本次问题、当前页面、明确选中的对象、同对象最近讨论，识别用户是在了解概念、准备操作、遇到阻塞，还是查证结果。页面提供语境，不能替代用户意图：在报告页问“怎样新建测试”，应解释创建流程，不硬套结果解读。

[scenario-plan.json](scenario-plan.json)登记首批12类场景、设计示例问题、所需上下文和候选工具/动作。示例用于设计，不是冻结效果题、训练标签或独立金标准；场景描述只用于路由，不能充当状态事实或文档依据。

首版建议用同一个query向量同时检索经过核对的场景描述和知识片段，不为意图分类额外发一次大模型请求。场景与文档采用同一Embedding配置，分别保存映射。取前1—2个候选场景，再以当前上下文和资料核对适用条件；场景只帮助选取回复步骤和相关资料，不增加权限、不替用户选择私人运行，也不硬过滤其他必要知识。

明确单场景就进入对应处理路径；复合问题可先处理阻塞项，再解释后续；多个互斥目标且无法核对时问一个关键问题。没有匹配场景时说明可处理范围，请用户补充目标，不把最高分场景强行套上。路由分数不是答案正确概率，阈值需用新的设计开发问题验证。

## 2. 引导式回复应包含什么

默认按用户当前进度给足可执行细节，通常采用下列顺序，但不把四个标题固定堆到每条回复里：

1. **先说明当前情况或目标。** 一两句直接回答问题，确认有证据的卡点；问概念时先用日常语言解释。
2. **讲清当前一步怎么做。** 写现有页面/按钮名称、需要选择什么或核对哪项；确实多步时用2—3个短步骤，当前最重要的动作做主按钮。
3. **说明这一步完成后看什么。** 给期望出现的区块、字段或状态，以及下一步的判断条件；这属于预期，不说成用户已经做过或一定会成功。
4. **给卡住时的对应分支。** 说明缺哪一项信息、从哪里取得；能用现有授权工具查到的先查，确需用户补充时一次问一个关键问题。

细心体现在具体和承接进度：第一次出现Worker时可说“负责执行测试的Worker”；字段已知时直接点出要核对哪个值；用户说找不到时缩小到一个页面/区块，不复读整套说明。步骤复杂可展开更细原文。必要后果、费用和未知仍紧邻相关动作显示。

答案的操作细节必须来自已核对的帮助章节和当前动作目录。引用优先贴在支持它的句子附近，点击展开到相关原文；不能为了显得详细而编造按钮、字段或运行结果。知识只解释流程，具体状态继续由本轮工具确认。

## 3. 从问题到解决的处理路径

| 场景 | 先核对 | 回复与下一步 |
|---|---|---|
| 不知道怎么开始 | 当前页与使用目标 | 给准备操作和入口，说明进入后需要选择什么 |
| 看不懂用例 | 已审核dev修订的条件/轮次/检查项 | 解释这题测什么，按原文指出判断依据，定位用例说明 |
| 准备创建运行 | 是否明确选择用例、兼容版本与预检范围 | 指引带入配置或打开工作台；最终创建留在原流程确认 |
| 环境阻塞 | 当前页是否允许环境取证，实际检查结果 | 指出已证实卡点，定位相应检查；不自动重启服务 |
| 查询执行进度 | 明确选中的自有运行/执行 | 区分排队、执行中、等待输入和结束，给当前有效步骤 |
| 解读结果 | 规则、业务事实、未知和证据范围 | 先给能确认的结论，再引导核对支持它的记录 |
| 找证据 | 用户想核对的结论与本轮来源 | 直接定位相关事件/原文，说明该记录能证明什么 |
| 版本不兼容 | 当前版本元数据和具体不兼容观察 | 解释当前差异，指引核对版本，不替用户登记或改配置 |
| 比较运行 | 是否明确选择两个满足原契约的运行 | 先核对可比条件，条件不足时说明缺哪项，不给伪胜负 |
| 导出或分享报告 | 当前报告和原页面导出能力 | 指到现有导出入口，说明导出范围；不新发下载或自动公开 |
| 缺陷复核与复测 | 已保存的缺陷/关联运行可读范围 | 解释现有修复复测流程；无新工具权限时给原页面入口 |
| 外部系统接入 | 是否有该系统资料、接口或网页及测试环境 | 先缩小接入路径，缺资料时问接口文档还是网页，不宣称接入完成 |

独立标注/校准页先执行原保护规则，不把样本分析路由到普通知识问答。脱离平台的问题可说明当前专注的平台场景，不为所有任意问题保证解决。

## 4. 场景切换与连续引导

先围绕一个目标，用户明确切换目标时重新识别。上一轮建议只是讨论语境，不证明用户已经操作；用户说“已经打开”后，可读取当前页面允许的信息重新核对，无法观察则明确只知道本人反馈。

候选追问根据场景和本次卡点生成，如“我没有看到这个入口”“检查仍然未响应”。点击先填入草稿，明确发送才开始新的Embedding/模型请求，不因点击引用/导航/场景按钮自动付费。

跨页后按新页面、身份与对象重新绑定会话和来源。若需要继续上一指引，实施时增加服务端核验的短期场景/上一动作交接，仅携带目标和步骤标识，不携带旧运行事实或旧授权；点击动作不代表步骤完成。没有交接实现时不承诺自动记住跨页流程；旧历史仅内存和配置漂移限制仍按主设计处理。

## 5. 期望回复示例

以下均为合成设计，不是模型实测。以“环境阻塞”为例，只有本轮观察确认Worker无响应时，才可以这样回复：

> 现在还不能开始，因为负责执行测试的Worker没有响应。
>
> 先打开「查看Worker与调度器检查」，核对Worker这一项。正常时应能取得与当前环境匹配的响应；如果仍未响应，先看该项返回的错误。
>
> 目前还不能确定是服务没启动还是连接问题。你把这一项的错误信息告诉我，就能继续缩小范围。

主动作仍只是导航。若工具已能读取具体错误，应先取得并解释，不让用户重复抄写；如果页面没有该区块或权限，改给原目录中确实允许的入口，不能照抄模板。

“结果已完成”的回复应引导核对具体证据，而不是反复提醒“不能判断”：

> 这次执行已经结束。下一步先核对提交和业务记录，才能判断目标是否完成。
>
> 打开「定位执行轨迹与输入处理」，找到提交调用及其返回，再对照业务记录。若返回未知，先查原请求，避免直接重复提交。

## 6. 实施与验证

并入P04-R3/R4，不另开赛事任务。R3包含场景候选检索、上下文适用判断、受控工具选择、按当前进度组织回答；R4包含对应引用、主动作和按场景追问。界面不新增长期常驻“场景说明”面板。

R5分别验证场景识别、证据支持、具体操作/预期是否准确、卡住分支是否有用、用户最终能否完成。加入跨页提问、复合问题、无对象、无匹配、版本漂移和越权样本请求；这些题需后续新编/核对/冻结，不能把本稿示例当独立效果成绩。保留失败与误路由，语气自然不等于问题已解决。
