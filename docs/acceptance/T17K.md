# T17K 验收：缺陷—修复—复测

入口：本地`http://127.0.0.1:5173/reports`，或运行详情中的“缺陷与报告”。使用统一登录的operator账号，密码读取本地配置，不写入本文件。验收不是要求立即执行付费实验；浏览、准备草稿和核对已有执行不调用模型。

## 团队操作

1. 在一条已结束且有客观规则失败的开发运行中查看原断言及业务事实，显式点击“归并缺陷候选”，再点击“查看候选与修复”。若没有失败候选，应显示空状态，不自动制造缺陷。
2. 查看“原失败 → 修复版本 → 复测结论”。点“核对失败证据”，应返回对应运行/执行的真实断言。候选不能等同已确认缺陷；先人工确认，再按实际改动关联同对象另一修复版本，永久保存前核对后果与依据。
3. 点击“准备复测草稿”。来源用例、故障、种子、次数和限制带入；仅当已关联版本当前可执行且同对象时预选该版本。打开草稿不创建运行、不消耗模型。没有新修复或历史源码不可用时应提示，不能伪造“已修复”。
4. 如确需创建新复测，人工核对差异与费用，经过环境预检后才确认创建。真实调用按本项另行确定的授权执行；本次实现验证未申请或消耗新模型额度。执行后回到缺陷面板选择实际验证运行与执行。
5. 查看条件check。只有对应修复版本、完整/未陈旧证据、相同条件及对应规则通过，才允许进入人工验证预览；“满足验证条件”不自动保存。最终需填写依据、勾选已查看证据，再核对并确认保存。
6. 展开历史记录，逐次跳转原失败和当次复测，核对原规则及SQL未被改写。只关联修复版本应仍显示“已关联修复”，不能显示“已验证”。

## 必查反例

| 情况 | 应观察到的行为 |
|---|---|
| 修复后仍失败或等待/取消/平台错误 | 不允许确认修复；保留原状态与证据 |
| 种子、用例、知识、模型、故障或额外输入不同 | 条件不一致或缺失，显示实际左右记录，不把它算同条件修复 |
| SQL快照/输出改变，但保存判定仍是旧passed | input_hash核对失败，不允许verified |
| 使用其他修复版本或另一账号的执行 | 版本不匹配或404；无跨账号内容 |
| 读取失败、关闭后重新打开、切换账号/路由 | 不沿用旧核对成功或旧表单；迟到响应不带入新上下文 |
| 保存回执丢失后重试 | 使用同一request_id返回原回执，不重复写入 |
| 离线控制对照 | 明确标离线，不宣传为真实模型修复或整体提升 |

手机390px、桌面、深浅主题和键盘均需可读；原证据链接、错误、费用与永久保存提示保留。只读核对不会开启模型、改变授权、替用户确认预约或自动启动Worker。
